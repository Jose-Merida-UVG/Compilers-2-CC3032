# Compiscript — Compilador: análisis y código intermedio (TAC)

**Demo (Lab 1 — léxico/sintáctico):** https://youtu.be/IowDshTJ0TI

Compilador (front-end) de Compiscript, un lenguaje pequeño similar a un
subconjunto de TypeScript (`let`/`const`/`var`, anotaciones `: type`,
funciones, clases con herencia, arreglos, control de flujo, etc. — ver
`src/grammar/Compiscript.g4` para la gramática exacta). Todo el código del
compilador vive en `src/`; `frontend/` es el IDE de navegador (React) que
sirve de interfaz gráfica. Cubre dos entregas del curso:

- **Proyecto 1 — análisis léxico, sintáctico y semántico:** ANTLR4,
  sistema de tipos, tabla de símbolos con manejo de ámbitos y un visitor
  sobre el árbol de parseo.
- **Proyecto 2 — generación de código intermedio:** si el programa no tiene
  ningún error (léxico, sintáctico ni semántico), se genera **código de tres
  direcciones (TAC)** como texto, y la tabla de símbolos se completa con
  tamaños, offsets, direcciones y registros de activación. Si hay cualquier
  error **no se genera TAC**. El compilador no ejecuta el programa ni produce
  código objeto.

Pipeline: `fuente → Lexer → Parser → SemanticChecker → TACGenerator → layout`.

Documentación:

- [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) — arquitectura completa:
  sistema de tipos, tabla de símbolos, el recorrido con el patrón visitor,
  generación de código intermedio (`src/tac/`), decisiones de diseño,
  división de trabajo (P1 y P2) y limitaciones conocidas.
- [docs/proyecto2/LenguajeIntermedio.md](docs/proyecto2/LenguajeIntermedio.md) —
  especificación del lenguaje intermedio: instrucciones, convenciones,
  justificación de cada decisión, ejemplos fuente → TAC por construcción y el
  algoritmo de reciclaje de temporales.

## Project structure

- `src/grammar/Compiscript.g4` — ANTLR4 grammar (source of truth for lexer/parser rules).
- `src/generated/` — build output regenerated by `make generate`; never edited by hand.
- `src/compiler.py` — shared pipeline (lex + parse + semantic check + TAC generation + error collection) used by both the CLI and the server.
- `src/error_listener.py` — custom ANTLR error listener that formats lexical/syntax errors in Spanish, with error recovery (keeps going after the first error).
- `src/semantic/` — semantic analysis: `types.py` (type system), `symbols.py` (symbol table + scope tree), `errors.py`, `checker.py` (the `SemanticChecker` ANTLR visitor implementing every rule, which also annotates each node with its type and symbol for the TAC phase), `layout.py` (sizes, offsets, addresses, activation records and class layouts for the symbol table).
- `src/tac/` — intermediate code generation (TAC): `generator.py` (`TACGenerator`, composes the four mixins), `gen_core.py` (declarations, expressions, conditions, arrays), `gen_control.py` (if/loops/switch/try-catch), `gen_functions.py` (functions, calls, return), `gen_classes.py` (classes, objects, inheritance), `emitter.py` (instruction emitter + temporary recycling), `instructions.py` (format conventions).
- `src/main.py` — CLI entrypoint (`make cli`).
- `src/server.py` — FastAPI backend: file-CRUD API over `workspace/` plus `/api/run`.
- `src/tests/` — automated test suite (`make test`): `src/tests/semantic/<categoria>/` with one battery of `.cps` cases per semantic rule category, and `src/tests/tac/<área>/` with valid/invalid cases per TAC rubric item (valid ones compared against a golden `.tac` file).
- `src/tools/` — vendored ANTLR jar used only for code generation.
- `frontend/` — browser IDE (Vite + React/TS): file explorer (selecciona el archivo de entrada), editor, panel de salida con errores navegables, visor de árbol de parseo, visor de tabla de símbolos (con tamaños, offsets y registros de activación) y visor de TAC — todos los resultados se muestran ahí, no solo en consola.
- `workspace/` — the IDE's working directory: `input/` has sample `.cps` programs (`input/comp-tac/` has the demo programs of the P2 rubric), `output/` has persisted run results (`.out`/`.tree`/`.symbols`/`.tac`).
- `docs/` — documentación de arquitectura, de la definición del lenguaje y del lenguaje intermedio (`docs/proyecto2/`).

## Requirements

- Java (JRE 11+) — only needed to run the ANTLR tool jar for code generation
- Python 3.9+
- Node.js — only needed for the frontend

## Install

```
make install
```

This creates a `.venv` at the repo root (if one doesn't already exist),
installs the Python dependencies from `src/requirements.txt` into it, and
runs `npm install` in `frontend/`.

Every Python-facing Makefile target (`run`, `cli`) auto-detects `.venv`:
if `.venv/bin/python3` / `.venv/bin/uvicorn` exist it uses those, otherwise
it falls back to whatever `python3`/`uvicorn` are on your `PATH`. You never
need to `source .venv/bin/activate` yourself — `make` handles it — but you
can if you want a shell with the venv active for e.g. running `python3`
ad-hoc.

The ANTLR tool jar is already vendored at `src/tools/antlr-4.13.2-complete.jar`
(used only for regenerating the parser, not at runtime).

## Generating the parser

Run this after any change to `src/grammar/Compiscript.g4`:

```
make generate
```

This runs `src/generate.sh`, which invokes the ANTLR jar and regenerates
`CompiscriptLexer.py`, `CompiscriptParser.py`, `CompiscriptVisitor.py`, and
`CompiscriptListener.py` into `src/generated/`. Files in `src/generated/`
are build output — never edit them by hand, edit the grammar and regenerate.

## Running a single file (CLI)

```
make cli FILE=<path-to-source-file>
```

e.g.:

```
make cli FILE=workspace/input/comp-tac/funciones-valido.cps
```

This lexes, parses, and (if there were no lexical/syntax errors) runs
semantic analysis on the file, printing every error found — in Spanish,
all in one run, not just the first — followed by a status line summarizing
the result. If there were **no errors at all**, it then prints the generated
three-address code (TAC); with any error, no TAC is generated.

## Running the tests

```
make test
```

Runs the full `pytest` suite:

- `src/tests/semantic/<categoria>/` has one battery of
  `valido_*.cps`/`invalido_*.cps` cases per semantic rule category (`tipos`,
  `ambito`, `funciones`, `control_flujo`, `clases`, `arreglos`, `generales`).
- `src/tests/tac/<área>/` has one folder per TAC rubric item
  (`declaraciones`, `aritmetica`, `logicas`, `arreglos`, `control_flujo`,
  `try_catch`, `funciones`, `recursividad`, `clases`, `herencia`,
  `temporales`, `tabla_simbolos`). Each `valido_X.cps` is compared with its
  golden `valido_X.tac`; each `invalido_X.cps` must report errors and produce
  **no** TAC. Extra tests check TAC invariants (`param` before every `call`,
  labels, temporary recycling, no leaks) and that every rubric row is covered.
- `src/tests/test_smoke.py` for grammar/pipeline regressions.

Narrow it down with e.g. `make test ARGS="src/tests/tac/control_flujo -v"`.
After an intentional change in the generator, regenerate the goldens with
`UPDATE_GOLDEN=1 make test ARGS="src/tests/tac"` and **review the diff**.

Los programas de demostración del IDE están en `workspace/input/comp-tac/`,
un `<área>-valido.cps` y un `<área>-invalido.cps` por cada punto de la rúbrica del
Proyecto 2.

## Web IDE (frontend + backend together)

```
make run
```

This starts both the FastAPI backend (`src/server.py`, port 8080, with
`--reload`) and the Vite frontend dev server together, and stops both on
Ctrl+C. Open the printed Vite URL (default `http://localhost:5173`) — it
proxies `/api/*` to the backend (see `frontend/vite.config.ts`).

The backend serves a small file-CRUD API over `workspace/` (repo root,
pre-seeded with sample `.cps` programs under `workspace/input/`) plus
`/api/run`, which runs a file through the same pipeline as the CLI
(`src/compiler.py`, shared by both entrypoints) and returns the errors, a
status message, a JSON parse tree, (when semantic analysis ran) a JSON
symbol table, and (only when there are no errors) the TAC and its statistics
(`tac`, `tacStats`) for the viewers.

In the IDE: **select the input file from the sidebar explorer** (or create
a new one with the ＋ button) and click **▶ Compilar**. Every result is shown
inside the interface, not just the terminal:
- Errors (lexical, syntax, and semantic — all of them found in that run,
  not just the first) and the status line print to the output panel.
- A **parse tree** tab opens automatically, with a collapsible visual
  representation of the syntax tree.
- A **symbol table** tab opens automatically when semantic analysis ran,
  showing every scope (global, function, class, block) nested as it was
  created, each with its declared symbols, kinds, types and — once the TAC is
  generated — size, offset and address, plus the activation record of each
  function and the field layout of each class.
- A **TAC** tab opens automatically when the program has no errors: the
  intermediate code with line numbers, highlighted labels/jumps/temporaries
  and a copy button. With any error the tab is hidden, a notice says that no
  intermediate code was generated, and each error in the output panel is
  clickable (it jumps to the line in the editor).

Each run also persists `output/<filename>/<filename>.out` (plain-text),
`.tree` (JSON parse tree), — when semantic analysis ran — `.symbols`
(JSON symbol table) and — when there were no errors — `.tac` (the
intermediate code; a stale `.tac` from a previous run is removed if the new
run has errors) into the workspace. All of them are reopenable from the
sidebar afterwards, and the `.tree`/`.symbols` files reopen in their
respective viewers rather than as raw JSON.
